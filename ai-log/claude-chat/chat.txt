The plan is good, and its structure and test list are solid. These are the changes I’d make, most important first.

Must change

Drop Supabase, use Docker Postgres. That means you write the auth yourself. Keep it minimal: email and password, bcryptjs for hashing, and a signed httpOnly session cookie (jose).
RLS needs a non-owner database role. Superusers and table owners bypass RLS, which would make your isolation test pass for the wrong reason. So:
Migrations run as the owner.
The app and the tests connect as a separate app_user role.
Use ALTER TABLE ... FORCE ROW LEVEL SECURITY.
Replace auth.uid() with current_setting('app.user_id').
Set the user per transaction, never per connection. Every request wraps its queries in BEGIN, then set_config('app.user_id', $1, true) (the true makes it transaction-local), then the queries, then COMMIT. A plain SET on a pooled connection can leak one user’s identity to the next request.
Don’t filter deleted_at in the RLS select policy. Soft delete is an UPDATE, and an UPDATE that makes a row invisible to the select policy can fail with “new row violates row-level security policy”, especially with RETURNING. Make RLS about ownership only, and hide deleted rows in the queries. Have the agent write a soft-delete test early.
Drop the plpgsql import_tasks function. Do the import in TypeScript inside one transaction instead: check existing title and due-date pairs, insert the valid rows, then commit. It’s easier to test, and easier for you to modify in the live session. Take a per-user pg_advisory_xact_lock at the start so two simultaneous imports can’t create duplicates.
Drop the table-wide unique index on title and due date. Duplicates are an import rule, and a user may legitimately create two similar tasks by hand. Check duplicates in the import code only.
Pin the Next.js version (15.x). Newer versions have renamed some conventions, such as middleware.ts, and surprises cost time here.

Details to get right

Row numbers: don’t use papaparse’s skipEmptyLines, because it loses the file position. Parse everything, number records yourself (header = row 1), and treat a row with all-empty cells (including ,,,) as blank and skipped. Trim headers, ignore extra columns, and reject the whole file if a required column is missing.
Priority: accept only whole numbers 1 to 5 after trimming, and require it. Blank means invalid.
Due date: make it required in the UI as well, since the CSV requires it. That avoids NULL edge cases.
Duplicates: the first occurrence wins, and later ones are rejected with “duplicate of row N”. If the first row was itself invalid, the later one is not a duplicate. Account duplicates also appear in the rejected list with their row numbers, so pass the row number through to the duplicate check.
Soft-deleted tasks don’t count as existing, and the README should say so.
Matching: exact match after trimming the title. Case-insensitive matching goes beyond the spec, so skip it unless you want it.
Rejected-rows CSV: quote fields properly when writing it, and test that it reads back correctly. Neutralise cells starting with =, +, - or @ so Excel doesn’t run them as formulas.
Tests: the tests need Postgres, so the README should say docker compose up -d, then npm run db:migrate, then npm test. Better still, have the vitest global setup run the migrations itself.
Extra RLS test: also test that a hard DELETE is impossible, with the DELETE privilege revoked from app_user.
Time: build fixtures/edge-cases.csv early, since the screen recording depends on it.

How auth works

Signup, login and logout are Server Actions in src/app/(auth)/actions.ts. They're thin wrappers that set the cookie and redirect. The logic lives in src/lib/auth/service.ts, which has no Next.js dependency so it can be tested directly.
Emails are trimmed and lowercased. Signup rejects an email that's already registered, ignoring case.
Passwords are hashed with bcryptjs at cost 12 and must be 8–72 bytes. bcryptjs silently ignores everything past 72 bytes, so signup rejects longer passwords.
Login returns "Invalid email or password." for both an unknown email and a wrong password. For an unknown email it still checks against a dummy hash, so the response doesn't come back faster.
Sessions (src/lib/auth/session.ts) use a random 32-byte token in the cookie: httpOnly, SameSite=Lax, 7 days, Secure when NODE_ENV=production. The database stores only the token's SHA-256 hash.
getCurrentUser() checks for an unexpired session and runs at most once per request. requireUser() redirects to /login if there's no user.
src/proxy.ts only checks that the cookie exists, for /tasks and /import. It imports the cookie name from a module with no dependencies, so it doesn't pull in pg.
Not every query goes through withUser. The users and sessions queries run on the pool directly, because login happens before there's a user ID to set. Every task query will go through withUser. The placeholder /tasks page already does, and I checked it against the running app.
Seed: scripts/seed.ts creates alice and bob, hashing their passwords at runtime, and can be re-run. It connects as the owner, because resetting a password on re-run needs UPDATE on users, which app_user doesn't have. The demo credentials are in the new README.md.
